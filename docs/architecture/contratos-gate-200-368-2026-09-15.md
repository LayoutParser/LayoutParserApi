## 1. `GET /api/workspaces/me`

**🇧🇷** [`Controllers/WorkspacesController.cs:38-68`](../../Controllers/WorkspacesController.cs).
Devolve o usuário atual + os workspaces em que é membro, criando o workspace pessoal de forma
idempotente na primeira chamada.

**🇺🇸** Returns the current user + workspaces they're a member of, idempotently creating the
personal workspace on first call.

```json
{
  "activeWorkspaceId": "3f2a…",
  "workspaces": [
    { "workspaceId": "3f2a…", "name": "Pessoal", "kind": "personal", "role": "owner", "createdAt": "2026-09-01T10:00:00Z" }
  ]
}
```

| Código | Quando |
|---|---|
| **200** | Sempre que a identidade resolve, mesmo que seja a primeira chamada (cria workspace pessoal na hora) |
| **401** | `ICurrentUser.UserId` não resolvido — **este endpoint é a exceção**: devolve `401` explícito (`{ "error": "Identidade não resolvida." }`), não `404` como o resto da API. Ver nota de divergência abaixo. |
| **503** | Falha ao consultar/criar workspaces (SQL fora do ar etc.) — fail-closed, nunca inventa um workspace "de mentira" |

**⚠️ Nota de divergência com o vocabulário geral de erro:** o padrão documentado em
[`contrato-rbac-erro-diff-mapping-fiscal-2026-09-10.md`§1](contrato-rbac-erro-diff-mapping-fiscal-2026-09-10.md#1-matriz-de-rbac-dos-endpoints-de-mapping-fiscal--rbac-matrix)
afirma "não existe `401`" na API — isso é verdade para os endpoints de mapping fiscal
(`RequireWorkspaceRoleFilter`), mas **não** para `GET /api/workspaces/me`, que devolve `401`
explícito por design (comentário na linha 35-36 do controller: "primeiro endpoint em que 'anônimo
responde algo' deixa de fazer sentido"). `GET /api/workspaces/{id}` (mesmo controller) já volta ao
padrão `404` uniforme. Trate isso caso a caso por endpoint, não como regra global da API.

`GET /api/workspaces/{workspaceId}` (mesmo controller, linha 75) devolve o mesmo shape para um
workspace específico, com 404 uniforme para "não existe" e "existe mas não é seu" (nunca 403 —
evita enumeração de workspace por ID).

## 4. Contrato de saída TCL/XSL/XSLT (compilação + edição manual de artefato)

**🇧🇷** [`Controllers/MappingCompilationController.cs`](../../Controllers/MappingCompilationController.cs).
`POST .../mapping-drafts/{id}/compile` (assíncrono via job) transpila as regras revisadas em
TCL/XSL/XSLT **de forma determinística** (`MappingDraftRuleTranspiler`/`DeterministicXslTranspiler`
— sem LLM na hora H). O resultado vira uma `MappingRelease`.

**🇺🇸** Reviewed rules are deterministically transpiled into TCL/XSL/XSLT (no LLM at compile time).
The result becomes a `MappingRelease`.

### Shape do artefato / Artifact shape

`GET .../mapping-drafts/{draftId}/releases/{releaseId}` (`MappingCompilationController.cs:382-421`):

```json
{
  "releaseId": "8f2c…",
  "engine": "xslt",
  "artifacts": [ { "kind": "xslt", "content": "…", "hash": "…", "generatedAt": "2026-09-10T12:00:00Z" } ],
  "status": "test_passed",
  "artifactSource": "compiled",
  "derivedFromReleaseId": null,
  "manualEditReason": null,
  "manuallyEditedArtifactKinds": [],
  "rulesDesynced": false,
  "eTag": "AAAAAAAAB9E="
}
```

- **`Hash`** por artefato (`MappingReleaseArtifact.Hash`) — base do `If-Match` do editor manual (§4b).
- **`status`** segue o ciclo de vida (`MappingReleaseStatus`): `draft_compiled` → `test_passed`/
  `test_failed` → `in_review` → `approved` → `published` → `deprecated` → `archived` (ver §7).
- **Imutabilidade pós-`publish`:** uma release `published` não é editada in-place — toda mudança
  gera uma nova `MappingRelease` (`MappingGovernanceController.cs:153`: "congela os artefatos —
  edição posterior exige nova revisão").

### 4b. Editor manual de artefato (issue #381) — novo desde 09-10

**🇧🇷** `PATCH .../mapping-drafts/{draftId}/artifacts/{engine}` — edição manual de TCL/XSLT
pós-compile. **Nunca sobrescreve a release-base**: cria uma `MappingRelease` **derivada** com
`ArtifactSource=manual_edit`, referenciando a origem via `derivedFromReleaseId`.

**🇺🇸** Manual post-compile edit of TCL/XSLT. **Never overwrites the base release** — creates a
**derived** `MappingRelease` with `ArtifactSource=manual_edit`, pointing back via `derivedFromReleaseId`.

| Código | Quando | Evidência |
|---|---|---|
| **200** | Edição salva — devolve a release derivada; `eTag` aqui é o **hash do artefato novo**, não o RowVersion genérico | `MappingCompilationController.cs:301-306` |
| **404** | Sem identidade/membership/draft de outro workspace | — |
| **403** | Papel fora de `mapper`/`fiscal_admin`/`owner` (RBAC mais estrito que a edição de regra — produz release candidata) | ADR §2.4 |
| **422** | `engine` fora de `{tcl,xslt}` (nunca `sysmiddle`); `content`/`justification` ausentes; sintaxe inválida; sem release compilada do draft/engine para servir de base | linhas 242-292 |
| **428** | `If-Match` ausente | — |
| **400** | `If-Match` não é base64 | — |
| **412** | Hash divergente do atual — corpo `{ "current": <artefato atual> }` | linha 294-299 |

Mesmo vocabulário 428/400/412 do `PATCH .../rules/{ruleId}` documentado em
[#376§2](contrato-rbac-erro-diff-mapping-fiscal-2026-09-10.md#2-vocabulário-de-erro-do-padrão-patch-mapping-draftsdraftidrulesruleid),
mas aqui o `200` **cria** um recurso novo (release derivada) em vez de editar in-place.

`rulesDesynced` é derivado (não persistido) — o front deve mostrar o selo "editado manualmente" e
desabilitar o diff-por-regra quando `true`. `ArtifactSyntaxValidator.TryValidate` valida sintaxe
TCL/XSLT antes de aceitar (não valida semântica/execução — isso é o test-run, §7).

## 5. `MappingExplanation`

**🇧🇷** [`Controllers/MappingExplanationController.cs`](../../Controllers/MappingExplanationController.cs)
(Slice 4, issues #226/#227) — **estava "NÃO EXISTE" na tabela original do gate #200 (agosto);
hoje é uma capacidade completa.** Rota:

**🇺🇸** Was "does not exist" in the original gate #200 table (August); today it's a complete
capability. Route:

```
GET /api/workspaces/{workspaceId}/mappings/{mappingId}/versions/{version}/explanation
```

Resolve `engine` a partir de `mappingId`: tenta primeiro como `draftId` (Slice 3) — se resolver,
usa o `engine` do draft (`tcl`/`xslt`); senão, cai para `MapperGuid` Sysmiddle (catálogo `tbMapper`,
não escopado por workspace — só a existência do mapper importa). Delega a um de 3 adapters
(`IMappingExplanationAdapter`: `tcl`/`xslt`/`sysmiddle` — `Services/Fiscal/{Tcl,Xslt,Sysmiddle}ExplanationAdapter.cs`).

**Deliberadamente sem `MappingEngineGuardFilter`** — explicar Sysmiddle é o caso permitido (spec §4:
Sysmiddle só `explain`, nunca `author`).

| Código | Quando |
|---|---|
| **200** | Um dos 3 adapters resolveu explicação — contrato canônico independente de motor |
| **404** | Sem identidade, sem membership no workspace, OU nenhum adapter resolveu (uniforme, sem distinguir "draft não existe" de "mapper Sysmiddle não existe") |
| **503** | Falha ao verificar membership/consultar draft |

Contrato canônico completo (campos, condições, nível de suporte, limitações por motor) em
[`adr-contrato-explicabilidade-fiscal-2026-09-07.md`](adr-contrato-explicabilidade-fiscal-2026-09-07.md)
— não duplicado aqui.

## 6. Capabilities Sysmiddle read-only — enforcement, NÃO um payload consultável

**🇧🇷** Issue #232 (CLOSED). [`Services/Filters/MappingEngineGuardFilter.cs`](../../Services/Filters/MappingEngineGuardFilter.cs)
recusa `engine=sysmiddle` no servidor — aplicado a `[ServiceFilter]` de nível de CONTROLLER em toda
rota mutável de `MappingDraftsController`/`MappingCompilationController`. Verifica **tanto query
quanto body** (string simples ou array — qualquer ocorrência de `"sysmiddle"` em qualquer um dos
dois basta pra bloquear com `422`). É defesa em profundidade, **não allowlist**: o filtro só
bloqueia `sysmiddle`, não valida que o valor é `tcl`/`xslt` — cada controller ainda precisa da
própria allowlist explícita (ex.: `MappingDraftsController.CreateDraft`).

**🇺🇸** Server-side rejection of `engine=sysmiddle`, applied controller-wide to every mutating
route. Depth-in-defense, not an allowlist — the filter only blocks `sysmiddle`; each controller
still needs its own explicit allowlist for accepted engines.

`MappingExplanationController` explicitamente **NÃO** aplica o filtro (é a rota de leitura
permitida — ver §5).

### ⚠️ O que NÃO existe: payload consultável de capability (issue #415)

O checklist original do #232 também pedia um endpoint tipo `GET .../capabilities` devolvendo
`{ author: false, compile: false, publish: false }` para o front decidir **antes** de renderizar
um botão (ex.: esconder "editar" sem precisar tentar e receber `422`). **Isso não existe.** Hoje a
capability só é observável indiretamente:

- tentando mutar e recebendo o bloqueio (`422` do `MappingEngineGuardFilter`), ou
- inspecionando `MappingExplanation.engine` na resposta de §5.

Rastreado como capacidade nova em **issue #415** — não tratar como resolvido. Se o front precisa
decidir a UI antes de tentar a ação, sinalizar a necessidade real do endpoint antes de abrir #415.

## 7. Bônus — Test Lab (diff por regra, diff release×release, cobertura de obrigatórios) + governança/ciclo de vida

**🇺🇸** Consolidates what was already communicated in prior issues, plus what's new since the

### 7a. Diff por regra (issue #367) — já documentado em #376, reconfirmado

`GET .../releases/{releaseId}` inclui `divergencesByRuleId` (`MappingCompilationController.cs:399-401`)
— mesma divergência de `testRunSummary.divergences`, agrupada por `ruleId`, para o front não
precisar filtrar no cliente.

### 7b. Diff release × release (issue #380) — novo desde 09-10

```
GET .../mapping-drafts/{draftId}/releases/diff?fromReleaseId={a}&toReleaseId={b}
```

Compara os XMLs **reais** produzidos por duas releases do MESMO draft (usa `ActualXml` persistido
no test-run de cada release — não é diff contra o gabarito, é release×release). Requer que
**ambas** as releases já tenham um test-run executado com sucesso; senão, `422` com orientação
explícita ("rode `POST .../test-runs` para a(s) release(s) faltante(s)"). Resposta agrega tanto a
lista plana (`diffs`) quanto agrupada por elemento de schema (`diffsByElement`) — mesmo padrão de
agrupamento de §7a, mas por nome de elemento em vez de por `ruleId`.

```json
{
  "fromReleaseId": "8f2c…",
  "toReleaseId": "9a1d…",
  "diffs": [ { "kind": "text", "xpath": "/NFe/infNFe/emit/CNPJ", "expected": "…", "actual": "…" } ],
  "diffsByElement": [ { "element": "CNPJ", "diffs": [ /* … */ ] } ]
}
```

### 7c. Cobertura de destinos obrigatórios (issue #380) — novo desde 09-10, distinto de `coveragePercent`

`GET .../releases/{releaseId}` inclui `requiredCoverage` (`MappingCompilationController.cs:417-420`):

```json
{
  "requiredCoverage": { "percent": 87.5, "uncovered": ["/NFe/infNFe/dest/CNPJ"] }
}
```

**Conceito distinto** de `testRunSummary.coveragePercent` (que é cobertura de **teste da fixture**,
não de campos obrigatórios do XSD). `requiredCoverage` cruza `minOccurs>=1`/`use=required` do XSD
alvo (resolvido via `fiscalProfile`, §3) com os `TargetRefs` das regras que compuseram a release.
**Degrada para `null`** — nunca lança — quando falta `fiscalProfile`, XSD não resolve, schema não
carrega, ou o elemento raiz não bate com o XSD configurado. Sem `fiscalProfile` setado (`PUT
.../fiscal-profile`, §3), `requiredCoverage` é sempre `null`.

### 7d. Filtros de listagem de release (issue #377) — novo desde 09-10

`GET /api/workspaces/{ws}/mapping-releases` (`MappingGovernanceController.cs:77-120`, qualquer
papel de membro) ganhou filtros opcionais combináveis: `status` (um valor do ciclo de vida —
`400` se fora de `MappingReleaseStatus.All`), `draftId` (GUID — `400` se malformado),
`environment`. Sem filtro, comportamento idêntico ao anterior (paginado por `page`/`pageSize`).

### 7e. Ciclo de vida estendido — deprecate/archive (issue #378) — novo desde 09-10

Além de `approve`/`publish`/`rollback` (já documentados em
[#376§1](contrato-rbac-erro-diff-mapping-fiscal-2026-09-10.md#1-matriz-de-rbac-dos-endpoints-de-mapping-fiscal--rbac-matrix)),
`MappingGovernanceController` ganhou:

| Rota | Transição | RBAC | Nota |
|---|---|---|---|
| `POST .../deprecate` | `published → deprecated` | `fiscal_admin`\|`owner` | Idempotente — re-deprecar já `deprecated` é no-op (200) |
| `POST .../archive` | `deprecated`/`test_failed`/`in_review` → `archived` | `fiscal_admin`\|`owner` | Estado terminal, só histórico/auditoria. Idempotente. `published` precisa ser deprecada antes (senão `422`) |

Ambas aceitam corpo opcional `{ "justification": "…" }`; transição de origem inválida devolve
`422` com mensagem PT-BR.
